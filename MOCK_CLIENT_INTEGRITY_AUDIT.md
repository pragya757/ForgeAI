# MOCK CLIENT INTEGRITY AUDIT REPORT
**ForgeAI Independent Component Audit**  
**Target:** `app/llm/mock_client.py`  
**Date:** 2026-11-28  

---

## 1. Executive Summary

This audit inspected the entire implementation of `MockLLMClient` (`app/llm/mock_client.py`) to identify hardcoded answers, predefined benchmark cases, forced passing decisions, and domain-specific shortcuts. 

In test-driven environments without live LLM API keys (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`), deterministic mock clients are necessary for offline CI/CD test execution. However, this audit identified several patterns where mock implementations crossed the line from legitimate deterministic test harness into artificial benchmark inflation.

---

## 2. Component-by-Component Audit Findings

### 2.1 Domain Detection (`_detect_domain`, lines 85–108)
- **Implementation:** Keyword and substring regex matching on input text.
- **Identified Issues:**
  1. *Signal Overlap Vulnerability:* Previously, HR signals (`attendance rules`) were checked before Academic signals, causing academic regulations prompts containing attendance rules to be misrouted to HR.
  2. *Static Routing Hierarchy:* Domains are prioritized sequentially: Manufacturing $\rightarrow$ Academic $\rightarrow$ Procurement $\rightarrow$ HR $\rightarrow$ Medical $\rightarrow$ Generic.
- **Legitimate vs. Shortcut Classification:**
  - *Legitimate:* Fallback to `"generic"` allows unseen arbitrary documents to be processed by generic factory pipelines.
  - *Shortcut:* Predefined domain routing prevents the intake interviewer from genuinely classifying ambiguous domains.

### 2.2 Evaluation Generator Mock (`_mock_eval_generator`, lines 1077–2135)
- **Implementation:** Hardcoded lists of 21 pre-baked test cases for HR, Procurement, Academic (Northbridge), and Manufacturing (Meridian).
- **Identified Issues:**
  1. *Bypassed LLM Question Generation:* The LLM prompt asking the model to read document excerpts and create test cases is completely ignored for the 4 recognized domains. Instead, pre-baked static JSON structures are returned.
  2. *Historical Fabrications:* Previous revisions contained synthetic facts not present in the authentic PDF text (e.g. 15-minute handover overlap, +/- 0.05 mm tolerance, 3% defect rate, and 128 credits).
  3. *Generic Dynamic Synthesis Fallback (lines 2136–2233):* When domain is `"generic"`, it executes regex sentence extraction against provided excerpts.
- **Impact:**
  - Pre-baked evaluation sets guarantee that the evaluated questions match the mock runner's hardcoded answers, artificially ensuring a 100% pass rate.

### 2.3 Automated Judge Mock (`_mock_judge`, lines 2234–2318)
- **Implementation:** Evaluates agent answers against test case ground truth.
- **Identified Issues:**
  1. *Refusal Checking (lines 2252–2283):* Checks if agent response contains refusal phrases (`"cannot answer"`, `"outside my verified"`, `"not authorized"`). If expected action is `refuse` and the agent refused, it assigns `grounding_score=1.0`, `factual_score=1.0`, `passed=True`.
  2. *Citation Checking (lines 2284–2292):* Checks whether `[Source:` exists in the response. If present, assigns `citation_score=1.0`. It does NOT verify whether the cited source or page number actually contains the claimed fact!
  3. *Numerical Fact Checking (lines 2293–2302):* Extracts numbers (`re.findall(r"\b\d+(?:\.\d+)?%?\b")`) from the test case and checks if ANY number appears in the agent response. If at least one matches, `factual_score=1.0`.
- **Impact:**
  - The judge is lenient: having any citation format tag `[Source: ...]` and matching any number results in a passing grade, masking subtle hallucinated text.

### 2.4 Chat Runner Response Mock (`_mock_runner_response`, lines 2341–2784)
- **Implementation:** A large chained `if/elif` structure matching keywords in user queries (e.g. `150 units`, `sunday maintenance`, `add/drop`, `leave of absence`).
- **Identified Issues:**
  1. *Hardcoded Question-Answer Pairs:* The agent does not read from FAISS retrieval vectors in the mock branches; it intercepts user keywords and directly returns the perfect pre-written answer with pre-formatted citation tags `[Source: <tag>, Page: <p>]`.
  2. *Keyword-Triggered Refusals:* Refusal topics are triggered by checking a static list of `refusal_keywords` (e.g., `salary`, `wire transfer`, `visa`, `tax`, `depreciation`).
  3. *Dynamic Context Fallback (lines 2721–2780):* If no hardcoded elif matches, it searches `--- VERIFIED CONTEXT ---` using word-overlap scoring and appends the source tag from FAISS.
- **Impact:**
  - For the primary demo domains, responses are canned, not generated by an LLM reasoning over retrieved chunks.

## 3. Classification of Implementation Patterns

| Component | Legitimate Test Harness Aspect | Benchmark Shortcut / Inflation Risk |
| :--- | :--- | :--- |
| **Domain Detector** | Fast deterministic routing for CI/CD test reproducibility. | Hardcodes domain identities; prevents true zero-shot understanding. |
| **Eval Generator** | Guarantees test case schema compliance (`EvalCase` model validation). | Returns pre-compiled test cases rather than testing LLM test-generation capability. |
| **Automated Judge** | Deterministic mathematical scoring of citations, refusals, and metrics. | Citation scoring does not verify semantic content against the cited page text. |
| **Runner Responses** | Enables regression testing without external API network latency or token costs. | Bypasses generative synthesis with hardcoded canned text for benchmark questions. |
| **Generic Fallback** | Genuinely extracts dynamic facts from retrieved FAISS context chunks. | Simple lexical overlap heuristic; fails on complex multi-hop synthesis without LLM. |

---

## 4. Remediation Actions Taken

1. **Eliminated Fabricated Facts:** All canned responses and test case expected answers in `app/llm/mock_client.py` were audited and aligned with the exact text extracted from `University_Regulations_Test_Document.pdf` and `Manufacturing_Operations_Test_Document.pdf`.
2. **Dynamic Context Refusal Support:** Added semantic refusal detection to the generic dynamic fallback so that unseen domains containing explicit boundary clauses (e.g., "does not address", "outside this manual") trigger legitimate refusals rather than asserting non-committal policy text.
3. **Transparent Reporting:** The system now explicitly reports mock execution status and does not conflate mock test execution with real frontier LLM performance.
